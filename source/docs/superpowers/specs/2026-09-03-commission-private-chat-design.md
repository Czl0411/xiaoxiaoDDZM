# 委托市场私聊化设计

## 目标

把委托市场的发布、查询和交易操作迁移到机器人私聊，避免在群聊中刷出市场清单、草稿和订单信息。服务或需求正式发布后，仍向已配置的委托群广播一张上架卡片。

DDZM 仅作为只读参考。本项目沿用其 Socket.IO 私聊房间识别、加入和定向发送模式，不修改 DDZM 文件。

## 用户行为

- 用户先打开机器人的个人资料并发送任意一条私聊消息，以建立可送达的私聊房间。
- 委托市场相关命令均在私聊中执行，包括帮助、发布服务、发布需求、确认或取消发布、市场与委托查询、详情、购买、接取以及订单处理。
- 用户在主群、委托群或绘图群发送上述命令时，机器人不执行命令。若该用户从未建立私聊，原群只提示“请私聊机器人使用该指令”；若已有私聊映射，机器人把指引发送到该用户私聊，原群只回复“圣喻已给你单独指引”。
- 私聊中的回复只回到发起消息所在的私聊房间，不能回到默认群或其他用户的私聊房间。
- 发布成功后，发布结果回到当前私聊，同时通过现有 `bounty` 群配置广播上架卡片。广播失败不回滚已完成的发布，但会写入明确的失败日志。

## 消息通道

### 私聊房间识别

Socket.IO 收到 `message:new` 时，以 `chatroomId` 判断来源：配置中的 `main`、`bounty`、`image` 房间属于群聊，其余房间属于私聊。私聊消息必须携带发送者平台 ID、消息 ID、文本内容和房间 ID。

首次收到某个私聊房间的消息后，将“平台用户 ID → 私聊房间 ID”保存到本项目数据库。映射以平台用户 ID 和房间 ID分别保持唯一；再次发现时更新原映射。

### 加入与恢复

网关维护群聊房间和私聊房间两类集合。启动或断线重连后，重新加入已保存且仍需监听的私聊房间。单个私聊房间加入失败只记录并延后重试，不影响三个群聊通道和其他私聊。

### 定向发送

Socket.IO 发送接口增加按真实 `chatroomId` 定向发送的能力。发送前加入目标房间，并校验目标不为空。私聊回复使用入站消息的房间 ID，不通过昵称寻找目标，也不依赖当前浏览器页面。

## 数据模型

新增 `direct_chats` 表：

- `platform_user_id`：平台稳定用户 ID，唯一；
- `chatroom_id`：私聊房间 ID，唯一；
- `discovered_at`：最近发现时间。

消息记录继续使用现有 `messages` 表；私聊消息的 `source_group` 使用稳定键 `direct:<chatroom_id>`，同时在运行期消息对象中保留 `source_type=direct` 与 `chatroom_id`。这样草稿归属仍由用户平台 ID隔离，而回复目标由房间 ID确定。

## 指令边界

建立一份委托市场私聊命令集合，直接复用当前配置中的命令别名，不另造一套命令。路由前执行通道检查：

- 私聊来源：允许进入现有委托市场处理逻辑；
- 群聊来源且无私聊映射：原群返回“请私聊机器人使用该指令”，不创建草稿、不查询清单、不改变订单；
- 群聊来源且已有私聊映射：向映射房间发送对应指引，原群返回“圣喻已给你单独指引”，仍不执行原命令；
- 其他非委托命令：保持当前群聊行为，不因本次改动迁移到私聊。

发布成功产生两个发送目标：当前私聊房间接收确认结果，`bounty` 群接收现有服务卡片或需求卡片。

## 安全与失败处理

- 忽略机器人自身发送的私聊消息，沿用消息 ID 去重。
- 私聊回复不受“群聊消息必须以 `/` 开头”的防误回复规则误拦截；用户命令本身仍按现有命令格式解析。
- 未知私聊命令不自动广播到任何群。
- 私聊房间不存在时，群内只能提示用户先私聊机器人，不能猜测房间 ID。
- 一个用户的草稿、库存、订单和查询结果不得发送到另一个用户的私聊房间。

## 验证

自动测试至少覆盖：

1. Socket.IO 能识别、加入、读取和定向回复私聊房间；
2. 重连后恢复私聊监听，单房间失败不影响群聊；
3. 群内发送委托命令只返回私聊引导且无数据库副作用；
4. 私聊 `/查看市场`、`/查看委托` 返回清单到同一私聊；
5. 私聊完成 `/服务`、`/需求` 草稿与 `/确认发布`；
6. 发布确认私聊成功，并向 `bounty` 群广播对应卡片；
7. 两个用户并发私聊时，回复和草稿不会串线；
8. 原有三个群聊的文字、图片 Socket.IO 测试继续通过。

完成自动测试后重启服务，并用一个真实私聊命令验证收取和回复，再验证一次发布广播链路。真实验证不得创建无法撤销的测试订单；如需发布测试项目，验证后立即使用现有取消/下架流程清理。
